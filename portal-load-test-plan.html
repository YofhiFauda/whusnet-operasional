01

Asumsi dasar

5.000/10.000 itu basis pelanggan terdaftar, bukan concurrent user — portal ISP residensial gak pernah dibuka bareng-bareng oleh semua orang di luar momen tertentu. Konkurensi diturunkan dari basis lewat rasio di bawah, bisa disesuaikan begitu ada data pemakaian riil.

Rasio 5% / 15% / 3% itu tebakan awal yang harus ditinjau ulang begitu ada data akses log portal sungguhan (mis. dari Cloudflare/nginx access log setelah portal live beberapa minggu). Jangan dianggap SLA — anggap starting point yang bisa dikalibrasi.

02

Load profile

Lima profil, tiap profil punya bentuk tahapan yang sama di basis 5.000 maupun 10.000 — cuma jumlah VU-nya beda 2×. Visual di bawah pakai angka basis 5.000; kolom 10.000 ada di tabel tiap kartu.

Empat pola dasar — persis 4 pilihan Load Profile di Postman

Postman (fitur Performance Testing, dibuka dari tombol Run collection → tab Performance) cuma nyediain 4 bentuk kurva ini — kebetulan pas persis buat 5 profil kita. Tiap kartu di bawah ditandai pill biru + field Postman yang perlu diisi.

Fixed

VU tetap sepanjang durasi. Field Postman: Virtual users saja.

Ramp Up

Naik bertahap dari Initial load ke Virtual users (maksimum), lama naiknya diatur drag-handle.

Spike

Naik dari Base load ke maksimum lalu TURUN LAGI ke base — bentuknya udah otomatis, tinggal drag durasi lonjakannya.

Peak

Naik dari Base load, DITAHAN di maksimum, baru turun — mirip Spike tapi ada fase hold di puncak.

Cek dulu sebelum jalanin Spike/Stress

Postman gak nerbitin angka batas VU resmi — dokumennya cuma bilang run lokal "dibatasi resource sistem", run cloud "gak dibatasi resource sistemmu (didistribusi ke banyak mesin)", tapi tetap kena batas plan Postman (Free/Team/dst beda kuota). Angka 750–2.500 VU di profil Spike/Stress kemungkinan besar melebihi kuota plan yang situ pakai. Cek dulu di Postman → Settings/Billing berapa VU maksimum akun situ, kalau lebih kecil dari tabel — turunin proporsional (mis. semua angka ÷4) atau jalanin Spike/Stress pakai tool lain (k6/Gatling) dan simpan Postman buat Fixed/Peak yang VU-nya lebih kecil.

Profil Stress gak bisa 1 form

Load Profile Ramp Up Postman cuma punya SATU tahap naik terus-menerus (Initial load → Virtual users), bukan tangga 5-step berhenti-naik-berhenti kayak tabel Stress di atas. Cara paling deket: set Initial load = 250 (5k) / 500 (10k), Virtual users = 1.250 (5k) / 2.500 (10k), Test duration = 25 menit, drag-handle ramp dipanjangin hampir sepanjang durasi (naik halus, bukan bertangga). Kalau butuh tangga step yang persis, pisahin jadi 5 run Fixed berurutan dengan VU tabel step masing-masing.

Perilaku satu virtual user

Satu sesi VU meniru pelanggan buka app: login sekali, baca-baca, jarang nulis. Think time 2–8 detik antar aksi — wajib ada, tanpa ini test cuma ngukur rate limiter, bukan performa API (lihat §04).

Loop aksi ber-bintang (branch) diulang 2–6× per sesi dengan bobot di atas, dipisah think time. Sesi yang bertahan >13 menit wajib memicu POST /auth/refresh otomatis (access token 15 menit) — relevan buat profil Soak, nyaris gak kejadian di profil pendek (Smoke/Peak/Spike).

Sengaja di luar loop utama

  • POST /auth/claim — gelombang provisioning awal (pelanggan baru klaim akun pertama kali), skenario terpisah, bukan bagian traffic harian steady.
  • bcrypt (BCRYPT_ROUNDS=12) bikin /auth/login & /auth/claim inheren lebih lambat dari endpoint baca data — dievaluasi pakai ambang sendiri, jangan disamain sama GET /me/* (lihat §05).
04

Rate limiter yang sudah aktif

Tiga limiter ini nempel di route sungguhan (AppServiceProvider) — kalau gak diperhitungkan, hasil load test cuma ngukur limiter-nya sendiri, bukan performa API.

LimiterBatasKeyEndpoint
customer-portal-api120/menitper access tokenSemua /me/*
customer-portal-auth5 / 15 menitIP + login_id/auth/login, /auth/claim
customer-portal-auth-ip30 / 15 menitIP saja/auth/login, /auth/claim
Wajib disiapkan sebelum profil apa pun jalan

Pre-provision token di fase setup, di luar jendela ukur. Login tiap VU sekali di awal, cache token-nya, sesi ukur cuma pakai /me/* + refresh berkala. Kalau load generator jalan dari sedikit IP sumber (lazimnya begitu), 750–2.500 VU yang login serentak dalam satu jendela pasti nabrak customer-portal-auth-ip (30/15menit per IP) — itu limiter-nya kerja, bukan API-nya lambat.

Kapasitas endpoint auth itu sendiri diuji terpisah, skala kecil (≤25 VU, mengikuti angka limiter), bukan digabung ke profil Peak/Spike/Stress.

05

Metrik & ambang

Ambang berlaku penuh di profil Peak Harian Normal; profil Spike boleh melar ×1.5 di kolom p95 selama error budget tetap dijaga.

Latensi & error, per kelas endpoint

Kelasp50p95p99Error budget
Baca data — GET /me/*<150ms<400ms<800ms<1% 5xx
Auth — login/claim (bcrypt)<300ms<800ms<1.500ms<0.5% 5xx
Refresh token<120ms<350ms<600ms<0.5% 5xx
Tulis — logout/ganti password<150ms<400ms<800ms<0.5% 5xx

Nol di semua kelas: 429 ke VU yang gak sengaja melebihi limiter (bukan skenario negatif yang memang disengaja), dan 500 yang nyangkut lebih dari satu request berturut (indikasi crash, bukan slow query).

Isian "Pass test if" di Postman

Postman cuma punya 5 metrik buat kondisi lulus — gak ada p50, paling deket p90. Isi per profil pakai tabel §latensi di atas, contoh buat profil Peak Harian Normal:

MetricConditionValue
p95 Response Timeis less than400 ms
p99 Response Timeis less than800 ms
Error %is less than1%

Buat profil auth-berat (kalau dites terpisah sesuai §04), ganti Value jadi 800ms/1500ms ngikutin baris "Auth" di tabel latensi. Avg. Response Time & Requests per second tersedia juga sebagai Metric kalau situ mau tambah kondisi throughput minimum.
